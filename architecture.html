How the LOB report system works

A plain-language overview for developers new to this project · 10-minute read · build instructions are in the build guide

The whole idea in one sentence: instead of re-reading every SharePoint file every time, we keep a list of all files and a short summary of each one, update only the files that changed, and build each team's report from that list.

1. What we are building

Our SharePoint library has a folder for each line of business (LOB), for example Transmission or Distribution. Each LOB folder has many sub-folders, and those have more sub-folders, with new files added every day.

Each LOB needs one HTML report that lists its files, grouped by area, with a short summary of every file and an overview of every area.

We build this with Copilot Studio workflows (automations, similar to Power Automate flows) and Dataverse (a database that comes with Power Platform).

2. Why the old version broke

The old version had three problems:

ProblemWhat happenedSimple explanation
It read everything, every runRuns got slower as the site grew, then timed out or got throttledLike re-reading a whole library to find out which books are new
It used search (RAG) to write the reportReports were missing content and changed from run to runSearch returns only the "top few" matches, never all files, so it can't produce a complete list
The AI wrote the HTMLReports were cut off halfway or had broken layoutAI models have a maximum answer length; a long report is longer than that

3. The new design in four steps

Think of a librarian with a card catalog. They don't re-read every book each morning. They write one card per book, update a card only when a book changes, and print the catalog from the cards.

  1. Find what changed. Every 30 minutes, for each LOB, ask SharePoint: "which files changed since my last successful check?" Only those files are processed.
  2. Summarize each changed file once. The AI reads one file and writes a short summary. We save it in Dataverse. If the file doesn't change, we never summarize it again.
  3. Summarize each area. For areas that had changes, the AI reads the saved file summaries (not the files) and writes a short area overview.
  4. Build the report without AI. A workflow takes the saved summaries and puts them into a fixed HTML template, the same way a mail-merge fills in a letter. Because a template builds it, the HTML is always complete and well-formed.

4. The pieces and how they connect

The arrows show who calls whom. WF0 runs on a timer and starts WF1 once for each LOB. WF1 finds the changed files and then calls WF2, WF3 and WF4, in that order. Every workflow reads and writes the Dataverse tables. WF5 runs once a week to catch deleted files.

5. Words you will see

TermMeaning
LOBLine of business, a top-level folder in the library. Each LOB gets one report.
AreaA sub-folder directly inside a LOB folder. Each area becomes one section of the report.
BreadcrumbThe deeper folder path below the area, e.g. Relays / 2026 / Q3, shown next to each file.
WatermarkThe date and time of the last successful run for a LOB. "Changed files" means "modified after the watermark."
ETagA version tag SharePoint gives every file. It changes whenever the file changes, so we compare it to know if a file really changed.
Child workflowA workflow that another workflow calls, like a function call in code.
StatusWhere a file is in the process: Pending (waiting for a summary), Summarized, Failed (AI couldn't summarize it after 3 tries), Skipped (file type we don't summarize), Deleted.
DirtyA yes/no flag meaning "something here changed and needs to be rebuilt."
EscapingReplacing characters like < and & with safe codes so a file name can't break the HTML.
RAGRetrieval-augmented generation: the AI searches for a few relevant pieces of text and answers from those. Good for questions, bad for complete reports.

6. Rules to keep (and why)

  1. Never scan the whole library in the normal run. Why: it's what made the old version slow and fail. Only WF5 does a full scan, once a week.
  2. Never let the AI write HTML. Why: AI answers have a length limit, and a long report gets cut off. The template is the only thing that writes HTML.
  3. Only move the watermark after a successful run. Why: if a run fails halfway, the next run should redo the same time window so no file is missed.
  4. Escape every value you put into HTML. Why: one file named Q3 <draft> & notes can break the whole page.
  5. Keep each LOB separate. Why: if one LOB has a problem, the others still get their reports.
Good to know: SharePoint downloads .html files instead of showing them in the browser. So we save reports as .aspx (with a site-owner connection) or send them as a Teams/Outlook attachment.
